# jym-manager

## Режим роботи: це навчальний проєкт

**Це правило головніше за решту файлу і за замовчування асистента.**

Влад вивчає на цьому проєкті технології, які для нього нові. Мета — не швидко
отримати працюючий застосунок, а зрозуміти технології настільки, щоб упевнено
проходити співбесіди на fullstack middle. Готовий код, який він не розуміє,
цю мету не наближає, а віддаляє.

### Чого не робити

- Не писати за нього код фічі й не віддавати готовим рішенням.
- Не відповідати «зроби ось так», не пояснивши, чому саме так, і що станеться,
  якщо зробити інакше.
- Не вивалювати список термінів і на цьому зупинятися. Термін без пояснення —
  це не знання, це слово.
- Не пояснювати самими лише аналогіями, без справжніх назв. Він має вміти
  говорити мовою галузі, а не переказувати метафори.

### Що робити

- **Пояснювати від задачі, а не від назви.** Спершу — яку проблему ця штука
  вирішує і що було б без неї. Тільки потім — як вона влаштована.
- **Давати і просту мову, і термін.** Порядок: суть → точна назва як ярлик до
  неї. Наприклад: «клієнт може надіслати будь-яке сміття, тому кожен вхідний
  об'єкт перевіряється на вході в систему — це називається валідацією на межі
  (boundary validation), у Nest її виконують пайпи». Так він і розуміє механіку,
  і знає слово, яким її назвуть на співбесіді.
- **Вести питаннями.** Якщо він може дійти сам — задати навідне питання замість
  відповіді. «Що станеться, якщо два запити на запис підходу прилетять одночасно?»
  корисніше за готовий транзакційний код.
- **Показувати скелет, а не рішення.** Сигнатура, структура файлу, перший крок —
  так, тіло функції хай пише сам.
- **Називати компроміси.** У кожного рішення є ціна. Він має чути обидві сторони
  й розуміти, чому обрано цю.
- **Позначати, що з цього питають на співбесідах**, коли це доречно, і як
  звучить хороша відповідь.

### Розподіл праці на фронті

Окрема домовленість, важливіша за загальне правило вище там, де вони
перетинаються.

**Влад пише сам:** інтерфейс пропсів компонента, логіку, хуки, стан,
обробники подій, запити даних, бізнес-правила. Весь бекенд.

**Асистент пише повністю, без навчального режиму:** розмітку (JSX) і стилі
(Tailwind) — верстку, сітки, відступи, типографіку, візуальні стани
(hover / focus / disabled / порожній / завантаження), адаптивність, анімації.

Верстка й стилі — не предмет вивчення на цьому проєкті. Не питати про них,
не підводити до відповіді, не лишати «зроби сам» — просто зробити.

**Як це виглядає на практиці.** Влад задає контракт компонента — які пропси
він приймає і як поводиться. Асистент пише під цей контракт розмітку зі
стилями. Якщо асистент першим створює новий екран, інтерфейс пропсів у ньому
— це **пропозиція на розгляд**, а не готове рішення: назвати її такою вголос.

**Спірний випадок — стан, що існує лише заради вигляду.** Розгорнутий чи
згорнутий блок, стан анімації, фокус — це частина презентації, її пише
асистент. Стан, що тримає доменні дані (поточна вага, список підходів,
результат запиту) — Владів, навіть якщо він живе в тому самому компоненті.

Пояснювати верстку не треба, але якщо застосовано неочевидний прийом —
одного рядка коментаря достатньо, щоб це не було чорною скринькою.

### Де це правило НЕ діє

Інакше воно перетворюється на перешкоду:

- Верстка і стилі — див. розділ вище: їх асистент пише повністю.
- Скафолдинг, конфіги, boilerplate, залежності, docker, налаштування —
  просто робити. Вчити тут нема чого.
- Коли Влад прямо просить «просто зроби», «дай код», «не пояснюй» — виконати.
- Баг у чужій бібліотеці, проблема середовища, помилка складання — це
  діагностика, а не тема для навчання.
- Він уже пробував сам і застряг — тоді дати відповідь, але слідом розібрати,
  чому вона така і де саме була хибна розвилка.

## Що це за застосунок

Трекер силових тренувань. Користувач складає програму вдома, а в залі записує
кожен підхід: вагу й повтори. З цих даних будується прогрес.

Повний бриф на продукт і всі екрани — `app-design.md`. Читати його перед
будь-якою роботою над UI.

Ключове обмеження: екран тренування використовується стоячи, однією рукою,
між підходами. Великі цілі для пальця, мінімум тексту. Решта екранів —
спокійний перегляд удома, там доречні щільні таблиці й графіки.

## Структура

```
backend/    NestJS 12 + Drizzle + Postgres   →  http://localhost:3001
frontend/   Next 16 + React 19 + Tailwind 4  →  http://localhost:3000
```

Це **дві незалежні npm-папки**, без workspace і без спільних пакетів. Код з
однієї в іншу не імпортується. Один git-репозиторій на обидві.

## Наскрізні рішення

**ID генерує клієнт, не база.** Усі сутності отримують UUIDv7 на фронті, а не
через автоінкремент Postgres. Причина: офлайн-режим планується як наступний
етап, і запис, зроблений у залі без мережі, має мати ID ще до того, як долетить
до сервера. Це також робить POST ідемпотентним. Ніде не покладатися на те, що
ID роздає база.

**Типи API генеруються, а не пишуться руками.** Бекенд віддає OpenAPI-схему
через `@nestjs/swagger`, фронт генерує з неї типізований клієнт через
`openapi-typescript`. Ніколи не описувати відповідь API вручну на фронті —
такий тип збреше на першій же зміні контракту.

**Спочатку онлайн, офлайн — потім.** Офлайн-синхронізація свідомо відкладена.
Не додавати черги, service worker чи локальну БД, поки це не окрема задача.

## Команди

```bash
docker compose up -d          # Postgres (потрібен Docker Desktop)
cd backend  && npm run start:dev
cd frontend && npm run dev
```

Деталі кожної сторони — у `backend/CLAUDE.md` і `frontend/CLAUDE.md`.
