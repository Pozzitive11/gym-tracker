# Налаштування БД під наявну автентифікацію

Робочий документ. Видалити, коли всі кроки закриті.

## Вихідна проблема

Код `src/auth/*` і `src/entities/*` написаний під **TypeORM** (`@nestjs/typeorm`,
`Repository`, `QueryFailedError`, `bcrypt`), але в `package.json` цих пакетів
немає. Встановлені `drizzle-orm`, `drizzle-kit`, `pg`, `@node-rs/argon2`.
Тобто бекенд зараз не збирається взагалі.

## Ухвалені рішення

| Питання | Рішення | Чому |
|---|---|---|
| ORM | **Drizzle** | Відповідає `CLAUDE.md`, залежності вже стоять |
| ID у `users` / `sessions` | **UUIDv7** | Однорідно з рештою сутностей проєкту |
| Джерело UUID | `DEFAULT uuidv7()` у Postgres 18 | DEFAULT спрацьовує лише коли значення не передали, тож «ID генерує клієнт» лишається в силі |
| Хешування | `@node-rs/argon2` замість `bcrypt` | argon2 встановлений, bcrypt — ні |
| `db:push` | не додаємо | Міграції комітяться; два шляхи зміни схеми рано чи пізно розійдуться |

### 6. Міграція і перевірка — ЗРОБЛЕНО

**Postgres 18 не стартував** — `Restarting (1)` у циклі. Причина не в проєкті:
образи 18+ змінили розташування даних. Том треба монтувати на
`/var/lib/postgresql`, а не на `/var/lib/postgresql/data` — образ сам кладе
дані в підкаталог `18/docker` (зроблено заради `pg_upgrade`).
Виправлено в `docker-compose.yml`, заведено новий том `postgres-data-18`.
Старий `jym-manager_postgres-data` лишився осиротілим — прибрати можна
через `docker volume rm jym-manager_postgres-data`.

`SELECT uuidv7();` на живій базі — **працює** (PostgreSQL 18.6). Запасний
план із пакетом `uuid` не потрібен.

Міграція `drizzle/0000_steep_gunslinger.sql` згенерована й накочена.
П'ять таблиць, індекси й каскади в базі збігаються зі схемою.

Автентифікація перевірена наскрізно:

| Перевірка | Результат |
|---|---|
| register (`Vlad@Example.COM  ` з пробілами) | 201, у базі `vlad@example.com` — @Transform працює |
| register тим самим email іншим регістром | 409 Conflict |
| login | 201 + кука |
| `/auth/me` з токеном | 200, `passwordHash` у відповіді немає |
| `/auth/me` без токена | 401 |
| refresh по куці | 201 |
| logout | 204 |
| refresh після logout | 401 — сесію в базі видалено |

## Ухвалені рішення по API програм

**Програма — агрегат.** Дні й вправи не мають самостійного життя: назовні
звертаються тільки до кореня, `/programs`. Окремих ендпоїнтів `/days`
чи `/day-exercises` не буде.

**Редагування — повна заміна, не часткове оновлення.** Клієнт завжди надсилає
повний стан програми. Наслідки:
- `UpdateProgramDto` = `OmitType(CreateProgramDto, ['id'])` **без** `PartialType`
- метод `PUT`, не `PATCH` — PATCH означає «ось зміни», PUT «ось повний стан»
- оптимістичне блокування (версія рядка / `If-Match`) свідомо не робимо:
  один юзер, одне вікно, ймовірність конфлікту нульова

**Запис у базу — видалити всі дні й вставити надіслані**, без звірки за `id`.
Простіше і швидше. Каскад на `program_days → day_exercises` робить це одним
DELETE. Усе в транзакції.

**⚠ УМОВА, від якої залежить попереднє рішення.**
Історія тренувань МУСИТЬ зберігати знімок, а не посилання на програму:
запис підходу тримає назву вправи текстом, вагу й повтори, і на
`day_exercises` не посилається.

Інакше delete-all при кожному збереженні програми або впреться в зовнішній
ключ, або знесе історію каскадом.

Це правильно й саме по собі: історія фіксує те, що сталося, а не вказує
на план, який відтоді змінився. Перейменування вправи не має переписувати
торішні записи.

Рішення незворотне після того, як накопичаться дані — тому зафіксовано зараз.

**`isActive`** — лишається в тілі запиту (клієнт надсилає повний стан).
Сервіс мусить обробити його транзакцією: зняти прапорець зі старої активної,
поставити на цю. Частковий унікальний індекс не дасть двом бути активними
одночасно.

**Модулі.** Один модуль `programs` на всю доменну область. Окремих модулів
для днів і вправ у дні НЕ буде: у них немає власних ендпоїнтів (звертаються
тільки до кореня агрегату) і немає сервісу, потрібного комусь іззовні.
Модуль на кожну таблицю — типова помилка; ділять по доменній області.

**Каталог вправ — відкладено, не відкинуто.** Коли з'явиться окреме створення
вправ (пошук, фільтр за групою м'язів, ознака «моя»), це буде свій модуль
`exercises` зі своїми ендпоїнтами. Тоді ж `day_exercises` перейде з тексту
на `exerciseId`, і стануть можливі графіки прогресу по вправі.
Зараз назва вправи зберігається текстом.

**Повторний запит із тим самим `id`:**
- `POST /programs` → **409 Conflict**. Клієнтські ID дають не ідемпотентність,
  а захист від дублікатів: другий виклик не створить другу програму.
- `PUT /programs/:id` → **200**. Повна заміна, повтор дає той самий результат.

Наслідок для майбутнього офлайн-режиму: якщо запит пішов, а відповідь не
долетіла, клієнт при повторі отримає 409 — і має трактувати це як «вже
збережено», а не як помилку.

## Крок 8. CRUD програм — ГОТОВО

Схема: `programs`, `program_days`, `day_exercises`. Модуль `programs`
(контролер, сервіс, 3 DTO). Глобальний `PostgresExceptionFilter`.

| Ендпоїнт | Код | Тіло |
|---|---|---|
| `POST /programs` | 201 | немає |
| `GET /programs` | 200 | плоский список, активна зверху |
| `GET /programs/:id` | 200 | дерево: програма → дні → вправи |
| `PUT /programs/:id` | 204 | немає |
| `DELETE /programs/:id` | 204 | немає |

Перевірено на живій базі:

- створення, повна заміна через PUT, перемикання активної, видалення з каскадом
- чужі програми (GET / PUT / DELETE іншим юзером) — 404, не 403
- повторний `id` — 409 з повідомленням за іменем обмеження
- порядок днів і вправ зберігається через `position`

**`PostgresExceptionFilter`** (`src/common/filters/`) мапить коди Postgres:
`23505` → 409 (повідомлення обирається за `constraint`), `23503` → 400.
`HttpException` пропускається далі — інакше `NotFoundException` із сервісу
перетворився б на 500.

**Лишилось дрібне:** `try/catch` з `isUniqueViolation` в `auth.service.ts`
тепер дублює фільтр — можна прибрати.

### Пастка середовища, витрачено час

Тестування REST через `bash` + `curl` на Windows ламає кирилицю: у базу
лягають `????` (перевірено — 6 байт, реальні знаки питання). Винна кодова
сторінка консолі, не застосунок. Тестувати з Node через `fetch` — там UTF-8
коректний.

### Далі

- `workouts` + `sets` — запис тренувань. Пам'ятати умову: історія зберігає
  ЗНІМОК (назва вправи текстом), а не посилання на `day_exercises`.
- `exercises` — каталог, окремий модуль. Тоді ж `day_exercises.name`

## Крок 9. Контракт відповідей + скафолдинг фронту — ГОТОВО

**Проблема:** `@ApiResponse({ status: 200 })` без `type` не описує форму
відповіді. Згенерована схема давала `content?: never` — фронт знав, що
надсилати, і не знав, що отримає.

**DTO відповідей** (`src/programs/dto/program-response.dto.ts`):
`DayExerciseResponseDto` → `ProgramDayResponseDto` → `ProgramListItemDto` →
`ProgramResponseDto extends ProgramListItemDto`. Класи оголошуються знизу
вгору: `@ApiProperty({ type: [X] })` звертається до X у момент виконання
декоратора, тож X має бути вище.

Валідації тут немає свідомо: перевіряють те, що приходить ззовні. Відповідь
формує сервер.

**Сервіс перелічує колонки в `.select({...})`.** Назовні більше не виходять
`userId`, `createdAt`, `position`, `programId`, `dayId`. `dayId` вибирається
для групування, але у відповідь не кладеться.

**`PUT /programs/:id` → 200 з повним деревом** (рішення змінено з 204).
Реалізовано як `findOne` ПІСЛЯ транзакції — всередині він ходив би іншим
з'єднанням з пулу і не бачив незакомічених змін, тобто повернув би старе
дерево без жодної помилки.

**Скафолдинг фронту:** `npm run api:types` (openapi-typescript),
`src/lib/api/client.ts` (openapi-fetch, `credentials: 'include'` заради
httpOnly-куки на іншому порту), `src/lib/id.ts` (uuidv7), `src/app/providers.tsx`
(TanStack Query, QueryClient у `useState` — щоб не шарився між SSR-запитами).

Перевірено компілятором: `list.data[0].days` і `one.data.userId` тепер
помилки збірки.
